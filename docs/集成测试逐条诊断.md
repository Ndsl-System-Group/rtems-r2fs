# RTFS Recovery 集成测试逐条诊断

## 1. 文档目的

这份文档不再讨论 integration 测试的总体分层，而是只聚焦 `test/integration/rtfs_recovery_integration_test.c` 中的 4 条 recovery 用例。

目标只有四个：

1. 说明每条用例到底想验证什么恢复语义。
2. 说明测试是如何构造该场景的。
3. 记录当前实际观察到的结果。
4. 将测试失败或 `IGNORE` 直接对应到生产代码缺口。

## 2. 当前结论总览

| 编号 | 用例 | 目标 | 当前状态 | 直接结论 |
| --- | --- | --- | --- | --- |
| `IT-REC-001` | `IntegrationRecovery_CreateCrashRemount_ShouldKeepCommittedFileVisible` | 已提交 create/write 在 crash remount 后仍可见 | `FAIL` | recovery replay 未实现，已提交对象未恢复 |
| `IT-REC-002` | `IntegrationRecovery_RenameCrashRemount_ShouldKeepCommittedResultVisible` | 已提交 rename 在 crash remount 后保持新路径可见 | `FAIL` | recovery replay 未实现，rename 结果未恢复 |
| `IT-REC-003` | `IntegrationRecovery_IncompleteTransactionCrashRemount_ShouldHideUncommittedFile` | 未完整提交事务在 crash remount 后不可见 | `IGNORE` | 缺少“识别并丢弃未完成事务”的恢复机制 |
| `IT-REC-004` | `IntegrationRecovery_ReclaimAfterCrashRemount_ShouldReleaseOldCowLpas` | recovery 后继续完成旧 COW LPA 的延迟回收 | `IGNORE` | 缺少 recovery replay 与 reclaim 状态重建 |

当前 recovery 主链路的共同缺口在 [src/communication/comm_api.c](/home/rtfs/src/communication/comm_api.c:258)：

- `comm_submit_fs_recover_from_db_request()` 现在仍是空实现。
- 挂载时 [src/fs/fs_handler.c](/home/rtfs/src/fs/fs_handler.c:2573) 的 `rtfsInitialize()` 会调用它。
- 但它没有做 journal 扫描、事务判定、状态回放，也没有重建延迟回收上下文。

## 3. 用例一：已提交 create/write 在 crash remount 后仍应可见

### 3.1 用例标识

- 编号：`IT-REC-001`
- 测试名：`IntegrationRecovery_CreateCrashRemount_ShouldKeepCommittedFileVisible`

### 3.2 目的

这条用例验证的是最基础的 recovery 正确性：

- 目录创建已提交。
- 文件创建已提交。
- 文件内容写入并 `fdatasync` 已提交。
- 如果此时掉电，下一次 remount 后，文件系统必须把这个结果重新恢复出来。

换句话说，它测的是“**已提交事务不能在 crash 后丢失**”。

### 3.3 流程设计

测试代码在 [test/integration/rtfs_recovery_integration_test.c](/home/rtfs/test/integration/rtfs_recovery_integration_test.c:27)。

执行步骤是：

1. `rtfsIntegrationFixtureFormatAndMount()`
2. `rtfsIntegrationMkdir("/rec")`
3. `rtfsIntegrationCreateFile("/rec/file.bin")`
4. `rtfsIntegrationWriteFile("/rec/file.bin", "recovery-create", ...)`
5. `rtfsIntegrationFixtureCrash()`
6. `rtfsIntegrationFixtureRemount()`
7. `rtfsIntegrationStatPath("/rec/file.bin")`
8. `rtfsIntegrationReadAt("/rec/file.bin", 0, ...)`

测试期望：

- `stat` 成功
- 文件类型仍是 regular file
- 文件大小等于写入长度
- 读回内容等于 `"recovery-create"`

### 3.4 测试如何构造该场景

这条用例没有做故障注入。

它构造的是最标准的“正常提交后掉电”场景：

- 写入路径通过 [test/integration/rtfs_integration_fixture.c](/home/rtfs/test/integration/rtfs_integration_fixture.c:986) 的 `rtfsIntegrationWriteFile()` 进入
- 该辅助函数内部会执行：
  - `open`
  - `write`
  - `fdatasync`
  - `close`

因此，这里并不是测试“缓存里是否可见”，而是在测试“**提交后的持久结果是否可恢复**”。

### 3.5 当前实际观察

串行执行：

```bash
make test-filter TEST_GROUP=integration TEST_FILTER=IntegrationRecovery_
```

观察结果：

- 该用例当前 `FAIL`
- 断言信息为：`Expected 0 Was 2`
- 这里的 `2` 是 `ENOENT`

也就是说：

- crash 前文件存在
- remount 后再查 `/rec/file.bin`，结果是“文件不存在”

### 3.6 生产实现缺失

这条用例失败，不是 create/write 提交路径没走通，而是 **remount 之后没有恢复提交结果**。

直接缺口：

1. [src/communication/comm_api.c](/home/rtfs/src/communication/comm_api.c:258) 的 `comm_submit_fs_recover_from_db_request()` 是空实现。
2. mount 初始化 [src/fs/fs_handler.c](/home/rtfs/src/fs/fs_handler.c:2573) 虽然调用了 recovery 入口，但没有任何 replay。
3. 因此 crash 前已提交的目录项、inode 映射、数据映射都没有在 remount 时重新装配为可见命名空间状态。

### 3.7 这条用例真正要求的恢复能力

至少需要以下能力闭合：

1. 从持久化 metadata / journal 中识别出“事务 1、2、3 已提交”。
2. 将这些已提交事务对应的目录项、NAT、SIT、SRMAP 状态 replay 到 mount 后的内存/缓存视图。
3. 确保 replay 后路径查找能重新看到 `/rec/file.bin`。

## 4. 用例二：已提交 rename 在 crash remount 后仍应保持结果

### 4.1 用例标识

- 编号：`IT-REC-002`
- 测试名：`IntegrationRecovery_RenameCrashRemount_ShouldKeepCommittedResultVisible`

### 4.2 目的

这条用例验证的是 rename 事务的恢复语义：

- crash 前 rename 已提交
- crash 后 remount 时，恢复结果必须体现“旧路径消失，新路径可见”
- 同时 inode 身份不能变化

也就是测“**命名空间变更事务在恢复后必须保持提交结果，而不是回退到旧名字**”。

### 4.3 流程设计

测试代码在 [test/integration/rtfs_recovery_integration_test.c](/home/rtfs/test/integration/rtfs_recovery_integration_test.c:80)。

执行步骤是：

1. `format + mount`
2. `mkdir("/rec")`
3. `create("/rec/file.bin")`
4. `stat("/rec/file.bin")` 记录 `before_st.st_ino`
5. `rename("/rec/file.bin", "/rec/file-renamed.bin")`
6. `stat("/rec/file-renamed.bin")` 记录 `after_st.st_ino`
7. 断言 rename 前后 inode 相同
8. `crash`
9. `remount`
10. 断言旧路径 `ENOENT`
11. 断言新路径 `stat == 0`
12. 断言 remount 后 inode 仍等于最初 inode

### 4.4 测试如何构造该场景

这条用例同样没有做故障注入。

它构造的是“已提交 rename 后立刻掉电”的场景，重点不是内容持久化，而是：

- 目录项删除与新增是否一起恢复
- inode 与路径的绑定关系是否按提交结果恢复

### 4.5 当前实际观察

同一次串行执行中，观察到：

- 该用例当前 `FAIL`
- 断言信息同样是：`Expected 0 Was 2`

这说明：

- crash 前 rename 已经对当前运行态可见
- remount 后查新路径失败，结果是 `ENOENT`

因此当前实现不是“恢复成旧路径”，而是更根本地“**没有恢复出这次 rename 事务的提交结果**”。

### 4.6 生产实现缺失

直接缺口与 `IT-REC-001` 相同，仍然是 recovery replay 未实现。

但这条用例比 create/write 多要求一层：

1. 恢复时不仅要恢复 inode 与数据块，还要恢复目录项变更。
2. 需要恢复“旧名字已删除、新名字已建立”的命名空间结果。
3. 需要保证恢复后的 inode 身份保持不变，而不是新建一个同名对象糊过去。

如果 recovery 只是“粗暴扫描现存 inode”，而不回放目录项更新，这条用例仍然会失败。

### 4.7 这条用例真正要求的恢复能力

至少需要：

1. replay rename 对父目录节点的修改。
2. replay inode 自身的更新。
3. replay 结束后，路径解析看到的是新路径，不是旧路径。

## 5. 用例三：未完整提交事务在 crash remount 后必须不可见

### 5.1 用例标识

- 编号：`IT-REC-003`
- 测试名：`IntegrationRecovery_IncompleteTransactionCrashRemount_ShouldHideUncommittedFile`

### 5.2 目的

这条用例测的是恢复机制的另一面：

- 不是“提交的必须保留”
- 而是“没提交完整的绝不能错误暴露”

也就是测“**恢复时必须能识别半事务，并把它当成未生效状态处理**”。

### 5.3 流程设计

测试代码在 [test/integration/rtfs_recovery_integration_test.c](/home/rtfs/test/integration/rtfs_recovery_integration_test.c:137)。

设计步骤是：

1. `format + mount`
2. `mkdir("/rec")`
3. `create("/rec/file.bin")`
4. 调用 `rtfsIntegrationFixtureSetStopAfterMetaWrites(&fixture, 1u)`
5. 调用 `rtfsIntegrationWriteFile("/rec/file.bin", "recovery-partial", ...)`
6. 期望返回 `EIO`
7. 断言 `rtfsIntegrationFixtureMetaWriteLimitHit()` 为真
8. `crash`
9. `remount`
10. 断言 `stat("/rec/file.bin") == ENOENT`

### 5.4 测试如何构造该场景

关键点在 [test/integration/rtfs_integration_fixture.c](/home/rtfs/test/integration/rtfs_integration_fixture.c:1368) 和 [test/integration/rtfs_integration_fixture.c](/home/rtfs/test/integration/rtfs_integration_fixture.c:98)。

夹具机制是：

1. `SetStopAfterMetaWrites(limit)` 设置一个 metadata 写成功次数上限。
2. 底层 `comm` 测试 hook 在每次块写时判断该 LPA 是否属于 metadata 区。
3. 当 metadata 写次数超过上限时，直接返回 `EIO`。

技术实质不是“文件内容写一半”，而是：

- 数据路径可能已经部分推进
- 但 metadata 提交过程被硬切断
- 从而构造出“盘面上有部分新状态，但事务没有完整闭合”的场景

这是最典型的 crash consistency 反例输入。

### 5.5 当前实际观察

当前这条用例在函数开头就执行了：

```c
TEST_IGNORE_MESSAGE(
    "Recovery replay is not implemented yet; comm_submit_fs_recover_from_db_request() is still a stub."
);
```

因此本轮实际结果不是 `PASS/FAIL`，而是：

- `IGNORE`
- 后续构造步骤当前没有真正执行到

所以“当前实际观察”只能写成两层：

1. **测试框架实际观察**：该用例被显式跳过。
2. **基于代码设计的预期观察**：如果 recovery 有能力识别未完成事务，那么 remount 后 `stat("/rec/file.bin")` 应返回 `ENOENT`。

### 5.6 生产实现缺失

这条用例要求的恢复能力，比前两条更严格。

前两条只要求：

- 已提交事务能恢复出来

这条还要求：

- 未完整事务能被识别出来
- 并且在恢复后被抑制，不出现在命名空间中

当前缺口包括：

1. 没有 journal replay。
2. 没有事务完整性判定逻辑。
3. 没有“已提交 / 未提交”边界识别。
4. 没有针对未完成事务的回滚或忽略策略。

因此现在即使把 `IGNORE` 去掉，得到的结果也没有工程意义，因为 recovery 主链路还不存在。

### 5.7 这条用例真正要求的恢复能力

至少需要：

1. 扫描 journal 区并重建事务边界。
2. 识别哪些事务已经完整提交。
3. 对未完成事务完全忽略，或将其影响从可见状态中剔除。

## 6. 用例四：recovery 后继续完成旧 COW LPA 的延迟回收

### 6.1 用例标识

- 编号：`IT-REC-004`
- 测试名：`IntegrationRecovery_ReclaimAfterCrashRemount_ShouldReleaseOldCowLpas`

### 6.2 目的

这条用例测的是 recovery 深水区语义：

- 覆盖写采用 COW，生成新 inode LPA 和新 data LPA
- 旧 LPA 不能立刻删，因为事务完成前还可能需要它们
- crash remount 之后，新版本必须保留
- recovery 完成并确认事务完成后，旧 LPA 必须被延迟回收

它测的是“**recovery 不只是恢复可见结果，还要恢复事务后续清理链路**”。

### 6.3 流程设计

测试代码在 [test/integration/rtfs_recovery_integration_test.c](/home/rtfs/test/integration/rtfs_recovery_integration_test.c:185)。

设计步骤是：

1. `format + mount`
2. `mkdir("/rec")`
3. `create("/rec/file.bin")`
4. 首次写入一整块 `A`
5. 用 `rtfsIntegrationReadCurrentFileMapping()` 读取当前 `old_inode_lpa` 与 `old_data_lpa`
6. 再用 `rtfsIntegrationWriteAt()` 在偏移 `0` 覆盖写一整块 `B`
7. 再次读取映射，得到 `new_inode_lpa` 与 `new_data_lpa`
8. 断言新旧 inode/data LPA 都不相等，证明发生了 COW
9. `crash`
10. `remount`
11. 调用 `rtfsIntegrationWaitForCommittedRecoveryJournal()`
12. 调用 `cowReclaimRegistryDrainCompleted()`
13. 调用 `rtfsIntegrationFlushMetadataToStore()`
14. 断言：
    - `new_inode_lpa` 对应块不是零块
    - `new_data_lpa` 对应块不是零块
    - `old_inode_lpa` 对应块是零块
    - `old_data_lpa` 对应块是零块

### 6.4 测试如何构造该场景

这条用例依赖两个观测辅助：

1. [test/integration/rtfs_integration_fixture.c](/home/rtfs/test/integration/rtfs_integration_fixture.c:1190) 的 `rtfsIntegrationReadCurrentFileMapping()`
   - 它读取当前文件 inode 对应的 node cache entry
   - 返回当前 inode LPA 和第一个 data LPA
2. [test/integration/rtfs_integration_fixture.c](/home/rtfs/test/integration/rtfs_integration_fixture.c:1252) 的 `rtfsIntegrationBlockStoreIsZeroed()`
   - 它直接检查测试盘面某个 LPA 的 4 KB 是否全 0

测试要验证的是：

- crash 后恢复出来的“现行版本”仍然占据 `new_*_lpa`
- 而旧版本对应的 `old_*_lpa` 会在 recovery 完成后的 reclaim 阶段被清空

### 6.5 当前实际观察

这条用例同样在开头就 `TEST_IGNORE` 了：

```c
TEST_IGNORE_MESSAGE(
    "Recovery replay is not implemented yet; reclaim-after-recovery semantics cannot pass until comm_submit_fs_recover_from_db_request() replays committed tx state."
);
```

因此当前真实观察只有：

- 测试被显式跳过

但它依赖的非 recovery 部分，其实已经有相当多实现：

- COW 覆盖会生成新 LPA
- 旧 LPA 会在提交时登记为 deferred reclaim

相关代码在 [src/file_inode/file_inode.c](/home/rtfs/src/file_inode/file_inode.c:670)：

1. 提交前收集 `old_data_lpas`
2. 收集 `old_node_lpas`
3. journal 提交后拿到 `tx_id`
4. 调用 [src/fs/cow_reclaim_registry.c](/home/rtfs/src/fs/cow_reclaim_registry.c:158) 的 `cowReclaimRegistryRegister()`

因此这条用例不是“完全没基础”，而是“**crash 之后无法把这条延迟回收链重新接上**”。

### 6.6 生产实现缺失

这条用例依赖的缺口比前三条更深：

1. recovery 要先恢复出已提交事务的最终可见状态。
2. recovery 还要恢复出“哪些旧 LPA 属于哪个 tx 的延迟回收计划”。
3. recovery 后要能重新触发 `tx complete -> pending reclaim -> completed reclaim -> drain` 这条链。

当前缺失主要有两类：

第一类：事务 replay 缺失

- `comm_submit_fs_recover_from_db_request()` 没有恢复已提交事务。

第二类：reclaim 上下文重建缺失

- [src/fs/cow_reclaim_registry.c](/home/rtfs/src/fs/cow_reclaim_registry.c:18) 里的 registry 是内存态链表。
- crash 之后，`pending_head` / `completed_head` 都会丢失。
- 当前没有任何持久化结构把这批“待回收旧 LPA”重新构建回来。

因此，即使 crash 前已经调用过 `cowReclaimRegistryRegister()`，remount 后那份待回收计划也不存在了。

### 6.7 这条用例真正要求的恢复能力

至少需要：

1. replay 已提交 COW 事务，恢复新 LPA 为现行版本。
2. 根据 journal / tx 信息重建旧 LPA 的 deferred reclaim 计划。
3. 在确认事务完成后，重新调用 reclaim 流程失效旧 LPA。
4. 将回收结果正确刷回 SIT / NAT / SRMAP 与测试盘面。

## 7. 四条用例的关系与修复顺序

这四条用例不是平行关系，而是严格递进关系。

### 7.1 第一层：先恢复“已提交结果可见”

- `IT-REC-001`
- `IT-REC-002`

这两条要求的是最基本的 recovery replay。

如果这两条不通过，说明系统连“把已提交事务恢复出来”都做不到，后面的“未提交剔除”和“延迟回收”都无从谈起。

### 7.2 第二层：再恢复“未提交结果不可见”

- `IT-REC-003`

这条是在第一层之上再增加事务边界判定能力。

### 7.3 第三层：最后恢复“回收链闭合”

- `IT-REC-004`

这条不仅要 replay 结果，还要 replay 事务后续的 deferred reclaim 状态，是 recovery 语义里最复杂的一层。

## 8. 当前建议

当前最合理的推进顺序是：

1. 先让 `IT-REC-001` 和 `IT-REC-002` 变绿。
2. 然后去掉 `IT-REC-003` 的 `IGNORE`，补“未完成事务不暴露”的能力。
3. 最后去掉 `IT-REC-004` 的 `IGNORE`，补 recovery 后的 reclaim 状态重建。

如果后续继续做 recovery 实现，这份文档可以直接作为逐条验收清单使用。
