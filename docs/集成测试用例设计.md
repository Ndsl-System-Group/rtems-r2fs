# RTFS 集成测试用例设计

## 1. 核心定义

这份文档是 RTFS 集成测试的设计说明，不是一次性执行记录。

它只回答三件事：

| 项目 | 含义 |
| --- | --- |
| 测什么 | 覆盖挂载、目录操作、文件读写、持久化、恢复、错误传播这些系统级行为 |
| 怎么测 | 优先走 RTEMS/VFS/POSIX 可见入口；只有元数据观测、故障注入、crash/remount 才使用测试夹具 |
| 如何判定有效 | 以外部可见语义和关键元数据状态转换为准，不以“某个内部函数是否被调用”作为成功标准 |

当前集成测试的职责，是把多模块协同路径串起来验证；它不替代单元测试。

对外语义以当前 RTEMS/VFS 实际暴露行为为准；如果入口层先拦截，则集成测试也以该结果为准。

## 2. 集成测试方案

### 2.1 测试分层

不要把不同验证目标混成一类。

| 层级 | 入口 | 目标 | 是否允许读取底层元数据 |
| --- | --- | --- | --- |
| API 集成测试 | `rtfsFsHandler`、RTEMS/VFS、POSIX 调用 | 验证真实文件系统语义 | 否，主要看 POSIX 可观察结果 |
| 元数据集成测试 | 文件系统操作触发，再读取盘面 | 验证 NAT/SIT/SRMAP/journal 状态一致 | 是 |
| 故障/恢复集成测试 | 文件系统操作 + 掉电点/写失败点 + remount/replay | 验证回放、回滚、延迟回收 | 是 |

### 2.2 应被真实触发的状态变化

| 组件 | 集成测试应观察到的变化 |
| --- | --- |
| `super` | 空闲段、当前写段、空闲 nid 链表、journal 边界变化并可持久化 |
| `NAT` | `nid -> node LPA` 的创建、更新、释放 |
| `SIT` | 新 LPA 变为有效，旧 LPA 在事务完成后失效 |
| `SRMAP` | data/node block 的反向映射被写入或更新 |
| cache | 读缓存、脏页、COW relocation、淘汰和回写路径被触发 |
| journal | 元数据进入 journal，提交后可应用，事务完成后可 reclaim |

### 2.3 覆盖率目标

| 模块 | 建议目标 |
| --- | --- |
| `src/fs/*.c` | 75%+ |
| `src/file_inode/*.c` | 75%+ |
| `src/dir_inode/*.c` | 75%+ |
| `src/cache/*.c` | 65%+ |
| `src/journal/*.c` | 65%+ |
| `src/communication/*.c` | 60%+ |

## 3. 当前测试夹具

这一节只描述当前代码里已经提供的夹具，以及它们各自负责的测试边界。

### 3.1 总览

当前代码里实际存在两类夹具：

| 夹具 | 主要入口层级 | 主要用途 | 不适合做什么 |
| --- | --- | --- | --- |
| `rtfs_rtems_mount_fixture` | RTEMS/VFS/POSIX | 验证对外文件系统语义 | 不提供块级故障注入、盘面元数据观测和 crash 点精确控制 |
| `rtfs_integration_fixture` | 测试盘面 + comm hook + mount 生命周期 | 验证元数据一致性、故障路径、crash/remount、恢复行为 | 不能替代纯外部 API 视角的语义验证 |

### 3.2 `rtfs_rtems_mount_fixture`

`rtfs_rtems_mount_fixture` 面向 API 集成测试，测试从 RTEMS/VFS/POSIX 可见入口进入。

它的作用是保证结论来自真实对外语义，而不是来自测试专用内部通道。适合验证挂载、目录操作、文件读写和错误码传播这类行为；不负责 NAT/SIT/SRMAP 观测，也不负责块级故障注入或 crash 前盘面构造。

### 3.3 `rtfs_integration_fixture`

`rtfs_integration_fixture` 面向元数据一致性、故障恢复和 crash/remount 场景。它直接控制测试盘面和 communication hook，并在挂载前通过 `mkfs` 机制生成最小可挂载且元数据自洽的初始镜像。

当前夹具提供的关键能力如下：

| 能力类别 | 作用 | 代表接口 |
| --- | --- | --- |
| 初始盘面构造与挂载生命周期 | 生成最小可挂载盘面，并支持 `format + mount`、`remount`、`crash remount` | `rtfsIntegrationFixtureFormatAndMount()`、`rtfsIntegrationFixtureRemount()`、`rtfsIntegrationFixtureCrash()` |
| 块级故障注入 | 模拟指定 LPA 读写失败、下一次写失败、下一次 data write 失败 | `rtfsIntegrationFixtureSetFailReadLpa()`、`rtfsIntegrationFixtureSetFailWriteLpa()`、`rtfsIntegrationFixtureFailNextWrite()`、`rtfsIntegrationFixtureFailNextDataWrite()` |
| 元数据写入中断控制 | 构造“写到一半停止”这类恢复场景 | `rtfsIntegrationFixtureSetStopAfterMetaWrites()` |
| 数据读写辅助 | 直接驱动文件指定偏移的读写，减少样板代码 | `rtfsIntegrationWriteAt()`、`rtfsIntegrationReadAt()` |
| 盘面与映射观测 | 读取当前文件映射，检查块存储内容与零块状态 | `rtfsIntegrationReadCurrentFileMapping()`、`rtfsIntegrationFixtureBlockStore()`、`rtfsIntegrationBlockStoreIsZeroed()` |

### 3.4 使用边界

- 验证对外语义时，优先使用 `rtfs_rtems_mount_fixture`。
- 需要观测盘面元数据时，使用 `rtfs_integration_fixture`。
- 需要块级故障注入、写入中断或 crash/remount 时，使用 `rtfs_integration_fixture`。
- 不要用 `rtfs_integration_fixture` 替代全部 API 语义测试，否则会削弱“真实外部入口”这一层验证。

## 4. 当前实现面

基线日期：`2026-05-28`

### 4.1 当前已注册的 integration 用例

当前 `test/integration` 中共注册 30 个 `RTFS_TEST`。

本轮整理后，生命周期与命名空间用例的结构发生了两类变化：

1. 生命周期 / 挂载
   删除了与最小挂载烟雾测试重叠的 `IntegrationLifecycle_MountStatReadDirStatvfs_ShouldExposeMinimalFilesystem`，保留 `IntegrationRtemsMount_FormatMountViaVfs_ShouldStatMountedRoot` 作为最薄外部 POSIX 入口测试，并将 remount 稳定性用例收敛并改名为 `IntegrationLifecycle_CleanRemount_ShouldPreserveRootViewAndSuperblockState`。
2. 命名空间
   将原先职责过厚的长名字边界与跨父目录 rename 用例拆分成多个更单一的测试，因此命名空间分类下的注册数量上升。

### 4.2 本次串行复验结果

这部分只保留本次实际复验过的结果，不再记录整段命令输出。

| 项目 | 结论 |
| --- | --- |
| `make test-list` | 成功列出全部测试；`integration` 组当前可见 30 个已注册用例 |
| `IntegrationFileIo_WriteUnmountRemountRead_ShouldPersistContent` | 本次串行单例复验通过 |
| `IntegrationRecovery_CreateCrashRemount_ShouldKeepCommittedFileVisible` | 本次串行单例复验失败，断言 `Expected 0 Was 2`，对应恢复后对象不可见 |
| `IntegrationRecovery_RenameCrashRemount_ShouldKeepCommittedResultVisible` | 本次串行单例复验失败，断言 `Expected 0 Was 2`，对应恢复后对象不可见 |
| 并发执行多个 `make test-filter` | 会触发 `waf` `.conf_check_*` 目录竞争，得到的是构建系统错误，不是文件系统语义结果 |

### 4.3 结果解释与边界

这里要特别区分两类失败：

1. 语义失败
   当前两条 `crash remount` 用例失败，说明“已提交事务在恢复后保持可见”这条恢复语义还没有闭合。
2. 构建竞争失败
   并发触发多个 `make` 时出现的 `.conf_check_*` 异常，不能计入测试结果。

### 4.4 已确认的语义边界

当前设计明确选择把 rename 的对外语义与 RTEMS/VFS 实际暴露行为对齐，而不是另外维护一套“handler 内部可做、VFS 对外不可见”的契约。

具体含义：

1. 对挂载后用户可见的语义，`rename(old, new)` 在 `new` 已存在普通文件时，当前结果定义为 `EEXIST`。
2. 这是 RTEMS 当前 `_rename_r()` 入口层行为，不是集成测试额外添加的限制。
3. 因此，RTEMS/VFS 层的集成测试矩阵不再把“replace 已存在普通文件”当作独立目标。

代价也要写清楚：

1. 这会让 handler 层潜在的更强 rename 能力不再自动成为对外契约。
2. 如果将来要验证 handler 内部 replace 语义，应单独放到更靠内层的测试里，而不是混进 VFS 语义测试。

## 5. 当前最值得先修的点

从本次串行复验看，优先级最高的问题已经收敛到 recovery 主链路：

| 项目 | 说明 |
| --- | --- |
| `IT-REC-001` 失败 | 已提交 create/write 在 crash remount 后不可见 |
| `IT-REC-002` 失败 | 已提交 rename 在 crash remount 后不可见 |
| `IT-REC-003` / `IT-REC-004` ignored | 依赖 recovery replay 主链路闭合后才有意义 |

因此当前更合理的推进顺序是：

1. 先修 `crash remount` 后已提交对象不可见的问题。
2. 再打开 `IT-REC-003`、`IT-REC-004` 这类依赖 replay 的用例。
3. 所有回归继续采用串行执行，避免把 `waf` 竞争错误误记成语义失败。
